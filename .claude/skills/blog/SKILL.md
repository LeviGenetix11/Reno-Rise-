# `/blog` — Reno Rise blog post generator

Static HTML site (no framework). Blog posts live at `blog/<slug>.html`, generated by
`tools/site/pages/posts.js` (basement-renovation topics) and `tools/site/pages/posts-flooring.js`
(flooring topics) via `node tools/site/build.js`. This skill only touches `posts.js`'s `POSTS`
array unless the topic is specifically flooring.

Do not invent a shortcut. Every step below exists because skipping it caused a real problem earlier
in this project (see "Lessons already learned the hard way," below).

---

## Inputs

- No args → pick the next batch from the CSV (see Step 1). Default batch size is **3 posts**,
  unless the user says otherwise. If genuinely unsure of the batch size for a *first* run in a new
  session, ask; otherwise keep the cadence already established with this user.
- User names a topic or keyword → confirm it exists in the CSV (or is a reasonable variant) and is
  not already in `used-keywords.md` before proceeding.

4. `SEO_brief/slideshow/onpage-seo-checklist.html` — the on-page SEO checklist (15 categories,
   80+ items). It's an HTML slideshow, not a doc; read the item text directly from the file.
5. `tools/site/pages/posts.js` in full — the exact shape every entry must match (`file`, `cats`,
   `tag`, `title`, `metaTitle`, `short`, `description`, `excerpt`, `img`, `alt`, `formType`,
   `dateLong`, `date`, `body()`, `faq`, `related`), plus the shared `hero()`, `TB_NOTE`, `SRC`

6. `tools/site/pages/util.js` — `U.toc()`, `U.backToTop()`, `U.sectionImage()`, `U.checkList()`,
   `U.faqItems()`, `U.notice()`. Use these for any post that crosses ~1500 words (see Step 6).

## Step-by-step workflow

### 1. Pick the primary keyword(s)

- Parse the CSV (`Keyword`, `Volume`, `Keyword Difficulty` columns).
- Cross-check every candidate against `used-keywords.md` (exact phrase) — never reuse a primary.
- Also check it doesn't just re-cover a topic already owned by an existing post in `posts.js` /
  `posts-flooring.js` (permits, cost, underpinning, egress, waterproofing, subfloor, flooring
  types, legal-suite-vs-finished, steps, before/after, walkout are already taken as of the last
  batch — check the file, this list will grow).
- Prefer decent volume, reasonable KD, genuinely basement-relevant (the CSV has some noise —
  generic bathroom-remodel rows etc. — mixed in from an adjacent keyword set; skip those).
- Announce the picks in one line each before researching: `Picking "<keyword>" (vol <V>, KD <KD>).`

### 2. Build the keyword cluster

4–5 secondaries per primary. Use close-match rows from the CSV first (mark mentally as
CSV-sourced). Fill any remaining slots with sensible made-up secondaries **only when the CSV has
no good match** — the user has explicitly approved this. Record the final cluster for
`used-keywords.md` at the end.

### 3. Research the real top-3 SERP

- `WebSearch` the primary keyword (add "Canada" or context if the raw query pulls US-heavy
  results — this business is GTA/Ontario, not US; see `reno_rise_gta` memory).
- `WebFetch` each of the top 3 genuinely-organic results (skip ads, forums, Pinterest/YouTube,
  and anything that's clearly a photo gallery with no real text — see the "before and after"
  precedent below for what to do if the whole SERP is like that).
- For each: extract format (listicle / tutorial / guide / comparison), approximate word count,
  every H2 topic covered, and any FAQ / "People Also Ask"-style questions.
- Target length within ~20% of the top-3 average.
- Cover every topic all three share. Add 1–2 topics none of them cover — this is usually a
  Toronto/Ontario permit angle, a tie-in to Reno Rise's own matching-service positioning, or a
  cross-link to another Reno Rise service/post none of the generic competitors have.
- Open with a direct, snippet-friendly answer to the query in the first ~100 words, with the
  primary keyword in it.
- Build a 4–8 question FAQ from real PAA-style questions surfaced during research (a second,
  more targeted `WebSearch` for "<topic> people also ask" often works).

**If the SERP is dominated by real-project photo galleries** (e.g. a "before and after" style
query): do not build a fake gallery. Reno Rise has no real projects to show and does not fabricate
case studies. Reframe as an honest, illustrative treatment of the same topic instead (see the
`basement-renovation-before-and-after.html` post for the precedent) and say so plainly in your
final report.

### 4. Write in the Reno Rise voice, compliance-adapted

Read `voice.md`, `humour.md`, `opinion.md`, `stories.md` and use them — but every one of those
files is written as if Reno Rise performs the work ("we fix it", "our team"). **Reno Rise is a
matching service, not a contractor.** Translate accordingly, same as every existing post already
does:
- "We fix / we handle" → "the contractor does X" / "a professional does X".
- Stories from `stories.md` are told as generic, illustrative scenarios ("A familiar scenario: a
  basement..."), never as something Reno Rise itself witnessed or did.
- The one statistic already vetted for use is the StatCan 32.7%-underground-economy figure
  (`SRC.statcan` in `posts.js`). Don't introduce a new number from `stats.md` unless it has a real,
  checkable URL — most of that file's figures don't, and posting an unverifiable stat as fact is
  a compliance risk, not just a style choice.
- **Never** a dollar figure or price range, anywhere. Reno Rise has a strict, deliberate
  no-price-ranges policy. Cost sections describe *drivers*, never numbers.
- **Never** imply Reno Rise did real project work. Stock photos get the same disclaimer every
  existing one uses: "Stock photo, illustrative only. It is not a Reno Rise project."
- Humour: 1 line per paragraph is the blog-post intensity per `humour.md`. Observational, never
  mean, always ends with reassurance — matches existing posts' tone (e.g. "That crack has a
  cousin, and they are both growing.").

### 5. Source images

**Check for a `.env`/`.env.local` file with `PEXELS_API_KEY` first** (`.gitignore` already
excludes these). If present, use the real Pexels API. If not — and as of this writing, no key has
ever been found or added — do this instead, in order of preference:
1. **Reuse the existing, already-credited stock library** (`images/stock/*.webp` — list the
   directory and pick contextually-fitting, unused-in-this-post images; reusing a photo across
   different pages sitewide is already normal practice here). This is the default; it needs no
   verification since every caption is already real and approved.
2. Only if nothing fits: Pexels' CDN can be hit directly (`images.pexels.com/photos/<id>/...`)
   without an API key — only the *search* endpoint needs one. You can `WebSearch` for a candidate
   photo page, `WebFetch` it to confirm the real photographer name, then `curl` the direct URL.
   **Visually inspect every candidate before using it** — this technique found at least one
   low-quality/mismatched result during earlier research; don't ship a bad photo to save a step.
   Never invent a photographer credit.

New images need: real filename (hyphens, descriptive), real alt text, WebP, correct
width/height attributes, `loading="lazy"` for anything below the fold (use `U.sectionImage()`).

Place a hero image (`hero()`) at the top, and additional images above the most visually relevant
H2s — not mechanically one per H2 if that would mean forcing an irrelevant stock photo in.

### 6. Write the post into `posts.js`

New entry in the `POSTS` array, matching the existing shape exactly. Reuse `hero()`, `TB_NOTE`,
`SRC`, `RENO`, `SUITE`, `X()`, `A()` already defined in the file.

- `metaTitle` + " | Reno Rise" → **50–60 characters total**. Count it, don't guess.
- `description` → **150–160 characters**. The file's own build-time check only warns outside
  145–165, so verify the tighter 150–160 range yourself.
- If the draft is likely to land near or over ~1500 words, add `${U.toc([...])}` right after the
  intro paragraphs and `${U.backToTop()}` right before the closing `` ` `` — every H2 needs a
  matching `id` and a TOC entry.
- 3–5 internal links in the body (not just the `related` footer array) — link to other Reno Rise
  posts/services with descriptive anchor text.
- 2–3 external links to real, already-known-good sources. Reuse `SRC` entries where the fact
  fits; only add a brand-new external URL after confirming it's real (WebFetch it) — never guess
  a government URL.
- No H3s needed; keep every section at H2, matching existing posts.
- FAQ: 4–8 entries, 2–4 sentences each, PAA-sourced per Step 3.

## Build and test — every batch, no exceptions

```
node tools/site/build.js
```
Must end with `no problems found`, `nav-check: all passed`, `flooring-check: all passed`. If a
check fails because it hardcodes an old total post count (this has happened twice —
`flooring-check.js`'s `cards.length === N` assertion, and `nav.mjs`'s blog-filter tests both
hardcode the blog-index card count) — **update the hardcoded number**, don't work around the test.

Then the full browser suite:
```
PW_DIR=<folder with playwright-core + axe-core + node_modules> node tools/site/browser-tests/nav.mjs
```
Must end `N/N passed`. Fix any real failure; don't ship with a known-broken check.

Grep the new content for accidental price figures and contractor-style claims before calling it
done:
```
grep -n '\$[0-9]' tools/site/pages/posts.js
grep -n "our team\|we perform\|we install\|Reno Rise does the\|Reno Rise performs" tools/site/pages/posts.js
```
Both should be empty (aside from already-existing, real, cited City subsidy dollar figures
elsewhere in the file, which are fine — they're sourced facts, not invented prices).

## Sitemap — the mistake to not repeat

`node tools/site/build.js` regenerates `sitemap.xml` with **every** page's `lastmod` bumped to
today, which is wrong for pages that didn't actually change. Do NOT just `git checkout
sitemap.xml` afterward either — that silently drops the brand-new post URLs from the sitemap
entirely (this happened once; it shipped a live site whose sitemap was missing the new posts for
several minutes before it was caught and fixed).

Correct sequence:
1. Let the build regenerate `sitemap.xml` fresh (it now has every URL, all dated today).
2. Merge: read the **last-committed** `sitemap.xml` (`git show HEAD:sitemap.xml`) as the source of
   truth for every URL's `lastmod` **except** the new post files and `blog/index.html` (which
   really did change — it gained new cards). Keep today's date only for those; restore every other
   URL's previous date from the committed version.
3. Diff the result (`git diff sitemap.xml`) and confirm only the intended URLs' dates moved.

## Keyword tracking

Append one row per new post to `used-keywords.md` (repo root), matching its existing table format:
primary keyword, secondaries (mark any invented one), the post's relative path, today's date.

## Commit — never push without being told

`git add -A`, then `git reset -q reno-rise-service-keyword-map.xlsx` (that file stays untracked),
commit locally with a clear message describing each post (primary/secondaries, format, word count
vs. the competitor average, what topic gap you closed, any compliance notes like an "and after"
reframe). **Do not push.** Report what was built and explicitly ask whether to push — approval in
one session/batch does not carry over to the next.

## Output summary (report to the user at the end)

For each post: primary keyword + secondaries, competitor format/length researched, the 1–2 topics
you covered that they didn't, word count, FAQ count, images used (and whether they're
newly-sourced or reused from the existing library), and any compliance adaptation worth flagging
(price-policy conflicts, before/after reframing, etc.). Then: build/test status, and the explicit
push question.

## Lessons already learned the hard way (don't repeat these)

- **Don't** assume all "cost breakdown"-style requests want dollar figures — Reno Rise's policy is
  drivers, never numbers. Confirm explicitly before ever publishing a price.
- **Don't** build a fake "before and after" gallery from stock photos, even if asked for
  "placeholders" — reframe honestly instead, and say so.
- **Don't** treat `reno-rise-service-keywords*.csv` / `LANDING-PAGE-PRIORITY-LIST.csv` as blog
  sources — those are for *service* pages (see the `/city-service` pattern in
  `tools/site/pages/city-service.js` if the user asks for city+service landing pages instead of
  blog posts; that's a different, related but separate workflow).
- **Don't** `git checkout sitemap.xml` reflexively after a build once new pages exist — check
  what changed first.
- **Don't** fabricate a Pexels photographer credit, a local by-law citation, or a stat without a
  real URL. If a source can't be verified (e.g. a municipality's site 403s automated fetches),
  say so and leave that specific claim out rather than guess.
